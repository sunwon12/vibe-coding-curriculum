# 제품04 — 안 무너지게: 테스트·모니터링·백업

## 🎯 이 스텝에서 하는 일 (한 줄)
AI가 **한 곳 고치다 다른 데를 부수는 걸** 자동으로 잡아내고, 사용자보다 **내가 먼저** 문제를 알고, **DB가 날아가도 되돌릴** 안전망 3종을 겁니다.

`⭐⭐ 보통 · 🕐 약 40분`

## 🔔 이 모듈이 필요한 신호
- AI에게 **한 곳을 고치면 엉뚱한 다른 곳이 깨진다.**
- **사용자가 버그를 나보다 먼저** 발견해서 알려준다("여기 안 눌려요").
- **DB(데이터 창고)가 날아갈까 봐** 불안하다.

## 왜 이렇게 하나

솔직하게 말할게요. **당신의 앱은 당신이 모르는 사이에 부서질 수 있어요.** 이걸 개발자들은 **회귀(regression, 잘 되던 게 다시 고장 나는 것)**라고 불러요. AI에게 "이 버튼 색만 바꿔줘"라고 했는데, AI가 **상관없는 파일까지 건드려서** 로그인이 안 되게 만드는 식이죠. 실제로 바이브 코딩에서 나오는 회귀 버그의 약 **23%가 AI의 '무관한 변경'**에서 나온다는 이야기가 있을 정도예요.

문제는 이런 버그가 **여러 파일을 넘나들며** 터진다는 거예요. 그래서 파일 하나만 보는 작은 검사로는 못 잡아요. **"사용자가 실제로 하는 행동 전체"**를 흉내 내서 확인해야 잡혀요.

그래서 이 모듈은 **화재경보기 + 소화기 + 되돌리기**를 답니다.

| 안전망 | 무엇을 막나 | 비유 |
|---|---|---|
| **테스트 (Playwright)** | 배포 전에 핵심 흐름이 깨졌는지 자동 확인 | 문 잠그기 전 "가스 잠갔나" 체크리스트 |
| **에러 모니터링 (Sentry)** | 라이브에서 터진 에러를 사용자보다 먼저 알림 | 화재경보기 |
| **백업 (db dump)** | DB가 날아가도 어제 상태로 복구 | 사진 찍어두기 |
| **프리뷰 (Vercel)** | 라이브에 반영 전에 사본에서 먼저 확인 | 실전 전 리허설 |

## 이렇게 하세요

### 1) 테스트 = 가드레일 (가장 먼저)

**커버리지(코드를 몇 % 검사했나) 같은 숫자는 신경 쓰지 마세요.** 당신에게 필요한 건 **스모크 테스트(smoke test, 앱에 불붙었나 연기만 확인하는 최소 점검) 딱 3~5개**예요.

- 홈 화면이 뜨나?
- 회원가입 / 로그인이 되나?
- **핵심 동작 하나**가 되나? (예: 할 일 추가, 글 작성)

이걸 **E2E 테스트(엔드투엔드, end-to-end — 사용자처럼 클릭해서 처음부터 끝까지 흐름 전체를 검증)**라고 해요. 도구는 **Playwright(플레이라이트)**를 씁니다. 두 가지 방법이 있어요.

- **클릭해서 자동 생성:** 코치가 `npx playwright codegen`을 켜주면, 당신이 브라우저에서 실제로 클릭·입력하는 걸 **테스트 코드로 그대로 받아 적어요.** 코딩 없이 시나리오가 만들어져요.
- **말로 시키기:** 코치에게 평문으로 "회원가입 후 대시보드에 도달하는지 검증하는 Playwright 테스트 써줘"라고 하면 코치가 작성해요.

**그리고 배포 전마다 이 테스트를 돌리세요.** 만들어만 두고 안 돌리면 없는 거예요.

> 💡 **AI가 스스로 검증하게 만들기 (검증 게이트).** 외국 고수들(Theo·Cole Medin·Matthew Berman)이 공통으로 쓰는 강력한 요령이에요.
> AI에게 기능을 "그냥 만들어줘"라고 하지 말고, **"성공했는지 확인하는 테스트를 먼저 만들고, 그 테스트가 통과할 때까지 고쳐"**라고
> 시키는 거예요. 그러면 AI가 자기 결과물을 **스스로 채점하며 될 때까지 반복**합니다. "되게 해줘"보다 훨씬 안정적이에요.
> 예: *"이 기능이 되는지 확인하는 테스트부터 만들고, 그 테스트가 초록불(통과)이 될 때까지 코드를 고쳐줘."*

### 2) 에러 모니터링 = 화재경보기

**"내 화면에선 잘 되는데요?"**의 함정을 조심하세요. 사용자는 **다른 브라우저, 느린 인터넷, 당신이 상상 못 한 입력(엣지케이스)**으로 앱을 써요. 당신 컴퓨터에서 멀쩡해도 남의 화면에선 깨질 수 있어요.

- **Sentry(센트리) 무료 티어**를 씁니다. 에러를 **월 5,000건**까지 무료로 수집해요.
- 설치는 코치가 `npx @sentry/wizard@latest -i nextjs` 한 줄로 해줘요.
- 설치 후 **일부러 테스트 에러**를 한 번 내서 Sentry에 진짜 잡히는지 확인하세요. (경보기 눌러보는 것)
- **새 에러가 나면 이메일 알림**이 오게 켜두세요. 그래야 사용자보다 먼저 알아요.
- 대안: 설치가 부담되면 **Vercel 내장 Observability(옵저버빌리티, 관찰 도구)**로 가볍게 시작해도 돼요.

> ⚠️ **쿼터(할당량) 주의:** 무한 반복(루프) 버그 하나가 몇 시간 만에 월 5,000건을 다 태울 수 있어요. **첫 에러부터 알림이 오게** 해서, 조용히 쿼터가 녹는 걸 막으세요.

### 3) 백업 = DB는 앱의 기억

**DB는 앱의 기억이에요.** 사용자·글·주문이 전부 여기 있어요. AI가 잘못된 **마이그레이션(DB 구조 변경 명령)**을 돌려서 테이블을 지우면 **영구 소실**이에요. 되돌릴 수 없어요.

> 💡 **예방책 — 바꾸기 전에 '되돌릴 SQL'을 미리 받아두기.** DB 구조를 바꿀 땐 AI에게 **"이 변경을 되돌리는 SQL(rollback)도 같이 줘"**라고 요구하세요.
> 그러면 잘못돼도 그 되돌리기 SQL 한 번으로 원상복구돼요. 예: *"이 테이블에 컬럼 추가하는 SQL과, 그걸 되돌리는 SQL을 둘 다 줘. 되돌리기 먼저 확인하고 적용하자."*

여기서 가장 중요한 정직한 사실 하나 — **Supabase 무료 티어는 자동 백업이 없어요. 백업은 당신 책임이에요.** (Pro 플랜 $25는 최근 7일 자동 백업을 줘요.) 무료로 할 수 있는 최선은 이거예요.

- **매일 자동 백업:** **Supabase 공식 GitHub Actions 워크플로**로 매일 자동 `db dump`(DB 통째로 파일로 뽑기)를 돌려요. `SUPABASE_DB_URL`(DB 접속 주소)은 **GitHub Secrets**(비밀 금고)에 넣고, 뽑힌 백업 파일은 반드시 **비공개(private) 저장소**에 보관해요.
- **간단하게:** 그것도 부담되면 **주 1회 수동**으로 코치에게 `supabase db dump`를 시켜서 파일을 받아두세요.
- **복원도 한 번 해보세요.** 백업은 **되살려봐야** 진짜예요. 안 해보면 정작 사고 때 안 될 수 있어요.

### 4) 스테이징 vs 프로덕션 = 리허설 무대

**Vercel Preview Deployments(프리뷰 배포)**는 **무료·자동**이에요. main이 아닌 **다른 브랜치(가지)를 push하면**, 앱 전체 사본을 **별도 URL**에 지어줘요. **main에 병합할 때만** 실서비스가 바뀌어요. 즉 라이브를 건드리기 전에 사본에서 리허설할 수 있어요.

> ⚠️ **프리뷰의 함정 — DB는 같이 안 갈라져요.** 프리뷰(사본)도 **기본적으로 실제 운영 DB를 그대로 건드려요.** 프리뷰에서 실수로 데이터를 지우면 **진짜 데이터가 지워져요.** 진짜로 격리하려면 **두 번째 무료 Supabase 프로젝트**를 하나 더 만들어 **개발용 DB**로 쓰세요.

**main(라이브)을 직접 편집하지 마세요.** 되돌리기 3층 얘기는 [[제품01-버전관리-Git-되돌리기]]를 보세요.

## 🤖 AI(코치)에게 줄 프롬프트

**스모크 테스트 만들기:**
```
회원가입 → 로그인 → [핵심 동작: 예 - 할 일 추가]이 되는지 검증하는
Playwright 스모크 테스트 3개를 만들어줘. 나는 완전 초보야.
- 각 테스트가 무엇을 확인하는지 한 줄씩 쉬운 말로 설명해줘.
- 그리고 배포 전에 이 테스트를 돌리는 방법을 알려줘.
- 나중에 테스트가 실패하면, 테스트를 지우지 말고 왜 깨졌는지 같이 찾자.
```

**Sentry 에러 모니터링 설치:**
```
이 앱에 Sentry를 설치해줘(무료 티어).
- 설치한 다음, 일부러 테스트 에러를 한 번 내서 Sentry에 진짜 잡히는지 같이 확인하자.
- 새 에러가 나면 내 이메일로 알림이 오게 켜줘. 첫 에러부터 알림 오게 해줘.
- API 키 같은 시크릿은 코드에 넣지 말고 환경변수에 둬.
```

**매일 자동 백업:**
```
Supabase 무료 티어는 자동 백업이 없다며. 매일 자동으로 DB를 백업하게 해줘.
- Supabase 공식 GitHub Actions 워크플로로 매일 db dump 하게 해줘.
- SUPABASE_DB_URL은 GitHub Secrets에 넣고, 백업 파일은 비공개(private) 저장소에 저장해줘.
- 다 되면, 백업 파일로 복원하는 연습도 한 번 같이 해보자.
```

## ✅ 여기까지 하면 이렇게 보여요

- **Playwright 스모크 테스트 3~5개**가 있고, 배포 전에 돌리는 법을 알아요.
- **Sentry(또는 Vercel Observability)**가 켜져 있고, 테스트 에러가 실제로 잡히는 걸 눈으로 봤어요. 새 에러는 **이메일로** 와요.
- **매일(또는 주 1회) 백업**이 비공개로 쌓이고, **복원을 한 번 해봤어요.**
- 큰 변경은 **프리뷰 URL로 먼저** 확인하고, main은 직접 안 고쳐요.
- **안 되면:** 설치·설정 중 빨간 글씨(에러)가 뜨면 전문을 그대로 코치에게 붙이세요. → [[스텝08-막혔을때-에러-읽고-디버깅]]

> 코치는 테스트 실행·Sentry 에러 확인·백업 1회·복원 체험이 확인되면 `진행상태.md`의 심화 트랙에서 이 모듈을 `- [x]`로 바꾸고 `상태.json`을 갱신합니다.

## ⚠️ 자주 하는 실수

- **테스트를 만들어만 두고 안 돌림.** 배포 전에 안 돌리면 없는 거예요.
- **AI가 실패하는 테스트를 '삭제'로 해결하게 둠.** 테스트가 빨개지면 그건 **경고**예요. 테스트를 지우지 말고 **코드를 고치세요.**
- **Sentry를 설치만 하고 안 봄.** 알림을 안 켜두면 사용자가 먼저 알아요.
- **"무료니까 데이터도 안전하겠지" 착각.** Supabase 무료는 **자동 백업이 없어요.** 백업은 당신 몫.
- **공개(public) 저장소에 백업을 올림.** 전 사용자 데이터가 통째로 노출돼요. **반드시 비공개**로.
- **복원을 한 번도 테스트 안 함.** 백업은 되살려봐야 진짜예요.
- **프리뷰가 실 DB를 건드리는 걸 모름.** 프리뷰에서 지운 게 진짜로 지워져요. 개발용 두 번째 DB로 격리하세요.
