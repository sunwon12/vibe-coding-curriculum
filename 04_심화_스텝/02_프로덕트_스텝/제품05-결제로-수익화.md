# 제품05 — 결제로 수익화 (MoR vs 국내 PG, 서버·웹훅 검증)

## 🎯 이 스텝에서 하는 일 (한 줄)
내 앱으로 **실제로 돈을 받되**, 한국의 법·세금 장벽을 넘고 **조작으로 공짜 결제되지 않게** 안전하게 붙입니다.

`⭐⭐⭐ 어려움 · 🕐 약 45분`

## 🔔 이 모듈이 필요한 신호
- 이 앱으로 **돈을 받고 싶다** (한 번 결제 또는 매달 구독).

## 왜 이렇게 하나

결제는 지금까지 중 **가장 무거운 주제**예요. 이유는 두 가지예요. ① 한국에서 진짜 돈을 받으려면 **법·세금** 문제가 걸리고, ② 돈이 걸리면 **공격자가 조작**하려 들거든요. 그래서 이 스텝은 코드보다 **판단**이 먼저예요.

### 먼저 기술이 아니라 법·세금

한국에서 남에게 **진짜 돈을 받아 매출을 내려면**, 대개 **사업자등록**이 필요해요. 개인이 사업자등록 없이 계속 돈을 받으면 문제가 될 수 있어요. 그런데 여기 합법적인 우회로가 있어요. **MoR**예요.

### MoR(Merchant of Record) — 사업자등록 없이 합법 판매

**MoR**는 "**법적으로 실제 판매자를 대행해 주는 업체**"예요. 대표적으로 **Lemon Squeezy**와 **Paddle**이 있어요. 이걸 쓰면 이렇게 돼요.

- 고객 카드 명세서에 찍히는 판매자가 **내가 아니라 그 업체**예요.
- 그래서 **내가 사업자등록을 안 해도 합법적으로 팔 수** 있어요.
- 각 나라의 **세금(VAT 등)을 그 업체가 대신 걷고 납부**해줘요.
- **환불·사기(chargeback)도 그 업체가 흡수**해줘요.

즉, MoR가 없애주는 건 "**전 세계에 물건 파는 판매자 부담 + 각국 세금 등록 부담**"이에요. 코드도 거의 안 붙어요.

⚠️ 단, **정직하게 짚을 게 있어요.** MoR가 없애주는 건 '**판매/각국 세금 등록 부담**'이지, '**내 소득신고 의무**'가 아니에요. 내가 번 돈에 대한 **국내 소득신고는 여전히 내 몫**이고, 매출이 커지면 결국 사업자등록을 하게 돼요. "MoR 쓰면 세금 다 끝"이 아니에요.

### 국내 PG(토스페이먼츠/포트원) — 돈만 옮기는 통로

**PG(Payment Gateway)**는 "**돈을 옮겨주는 통로**"일 뿐이에요. 국내엔 **토스페이먼츠**, 여러 PG를 하나로 묶어주는 **포트원** 등이 있어요. MoR와 결정적으로 달라요.

- **법적 판매자는 나**예요. → **사업자등록·세금·분쟁 처리가 전부 내 몫**이에요.
- 대신 **국내 수수료가 싸고**, 특히 **카카오페이** 결제 경험이 매끄러워요.

그리고 흔한 오해 하나. **Stripe(스트라이프)는 한국 개인이 직접 계정을 못 만들어요** — 미국 등의 법인이 있어야 해요. "해외에서 유명하니 Stripe 써야지" 했다가 막히는 경우가 많아요.

### 상황별 처방 (표)

| 내 상황 | 이걸 쓰세요 |
|---|---|
| 사업자등록 **없음** + 글로벌/디지털 상품 | **Lemon Squeezy / Paddle** (MoR) |
| 국내 고객 위주 + 사업자등록 **있음** | **토스페이먼츠 / 포트원** (카카오페이 정기결제 등) |
| 미국 등 법인 **있음** | **Stripe** |

**한 줄 처방:** 이제 막 시작한 한국 비개발자가 "**일단 돈 받아보고 싶다**"면, 디지털/SaaS 상품은 **Lemon Squeezy 또는 Paddle로 시작**하세요. 사업자등록·세금 장벽을 통째로 건너뛰고, 코드도 거의 안 붙어요. 나중에 국내 비중이 커지고 사업자등록을 내면 그때 **토스/포트원**으로 옮기면 돼요.

**수수료 참고**(가입 시점에 반드시 공식 페이지 재확인):
- Lemon Squeezy / Paddle ≈ **5% + 건당 $0.50** (세금·구독 관리·사기 방지 포함된 값이에요).
- 토스페이먼츠 카드 ≈ **3.4% + 부가세** 수준.

MoR가 수수료가 더 비싸 보여도, 그 안에 세금·사기·구독 관리가 다 포함돼 있어요. "싼 수수료 vs 신경 안 써도 되는 편함"의 트레이드오프예요.

### 안전의 황금률: 클라이언트를 절대 믿지 마라

여기가 결제에서 **가장 중요**해요. 돈이 걸리면 공격자는 개발자도구(F12)로 브라우저가 보내는 값을 **조작**해요.

"얼마인지(**금액**)"와 "결제가 성공했는지(**상태**)"는 **반드시 서버에서 검증**해야 해요. 브라우저가 보내는 값을 그대로 믿으면 안 돼요.

**❌ 틀린 패턴 (해킹당함):**

```
브라우저가 서버에 "paid=true, amount=100원" 이라고 보냄
   → 서버가 그대로 믿고 유료 권한을 줌
   → 공격자가 F12로 amount=100 을 amount=1 로 바꿔 헐값 결제
     또는 아예 paid=true 만 위조해 공짜로 이용
```

**✅ 옳은 패턴 (서버가 진실을 확인):**

```
① 주문 생성 시, 서버가 "이 주문은 얼마"인지 실제 금액을 DB에 기록
② 고객이 결제사(Lemon/토스) 창에서 실제로 결제
③ 결제사가 내 서버로 웹훅(webhook)을 보냄
     → 웹훅 = "결제 끝났어요"라고 결제사가 내 서버 뒷문으로 직접 알려주는 신호
④ 서버가 그 웹훅을 세 가지로 검증한다:
     (a) 서명 검증 — 이 신호가 진짜 결제사가 보낸 게 맞는지 (raw body로)
     (b) 금액 일치 — 실제 결제된 금액이 ①에서 DB에 적어둔 금액과 같은지
         (또는 결제사의 confirm/verify API로 다시 물어봄)
     (c) 중복 방지 — event.id 를 UNIQUE로 저장해 같은 결제를 두 번 처리 안 함
         (= idempotency, 멱등성: 같은 요청이 와도 결과가 한 번만 반영됨)
⑤ (a)(b)(c) 셋 다 통과했을 때에만 유료 권한을 준다
```

핵심 문장 하나만 외우세요. **권한 부여는 오직 서버에서만.** 브라우저가 "나 돈 냈어"라고 말하는 걸 근거로 권한을 주면 절대 안 돼요. 결제사가 서버 뒷문(웹훅)으로 직접 확인해 준 것만 믿어요.

여기서 **웹훅 서명을 검증**하는 이유도 같아요. 웹훅 주소는 인터넷에 열려 있으니, 누구나 "결제 완료됐어요"라는 가짜 웹훅을 내 서버로 쏠 수 있어요. **서명 검증**은 "이 신호가 진짜 결제사가 보낸 게 맞는지" 도장을 확인하는 거예요. 이때 **raw body**(가공 안 한 원본 데이터)로 검사해야 해요 — 중간에 형식을 바꾸면 도장이 안 맞아요. 이 부분은 코드가 까다로우니 **결제사 공식 문서의 방식을 정확히** 따라야 해요.

## 이렇게 하세요

1. **먼저 판단하세요: MoR인가, 국내 PG인가.**
   - 위 표로 정하세요. 헷갈리면 코치에게 "내 상황은 [사업자등록 유무/국내냐 글로벌이냐]인데 뭘 써야 해?"라고 물어요. 대부분 처음엔 **Lemon Squeezy/Paddle**이 답이에요.

2. **결제사 계정을 만들고 테스트 모드를 켜세요.**
   - 결제사(Lemon Squeezy 또는 토스페이먼츠)에서 가입 → **상품/가격 등록** → **테스트 모드**(가짜 카드로 연습하는 모드) 켜기. 버튼 누르는 부분은 당신이, 코치가 짚어줘요.

3. **코치가 결제 흐름을 붙입니다 — 웹훅 검증이 핵심.**
   - 코치가 주문 생성 → 결제창 → **웹훅으로 검증 → 권한 부여**까지 붙여요.
   - 웹훅 **시크릿(비밀 키)**과 결제사 API 키는 `.env`에만 넣고, **`NEXT_PUBLIC_`은 절대** 안 붙여요(AI03과 같은 규칙).

4. **테스트 결제로 "조작 방어"를 직접 확인하세요.**
   - 정상 테스트 결제 → 권한이 잘 부여되는지.
   - (코치가 도와서) 금액을 조작한 요청 → **거부되는지**. 이게 확인돼야 진짜 안전해요.

5. **잘 되면 코치가 저장점을 찍습니다.**

## 🤖 AI(코치)에게 줄 프롬프트

**안전 규칙을 프롬프트에 박아 넣는 게 핵심**이에요.

```
계획 먼저 말해줘. 먼저 결제 흐름 전체를 주석으로 설명하고, 그다음에 코드를 짜자.

내 Next.js(App Router) + Supabase 앱에 결제를 붙여줘. 나는 완전 초보야.
결제사는 [Lemon Squeezy / 토스페이먼츠 중 택1] 로 할게.

절대 지킬 규칙:
① 클라이언트(브라우저)가 보내는 금액이나 '결제 성공' 상태를 신뢰하지 마.
   가격은 서버/DB에서만 결정해.
② 유료 권한 부여는 오직 서버(웹훅 라우트 또는 서버 confirm API)에서만 해.
③ 결제 확정은 웹훅으로 처리하고, 웹훅 핸들러 안에서 세 가지를 모두 확인해:
   (a) 서명 검증 (반드시 raw body 로),
   (b) 실제 결제 금액이 DB에 기록한 주문 금액과 일치하는지,
   (c) 같은 event.id 는 UNIQUE 로 저장해 한 번만 처리(idempotency).
   이 셋을 다 통과해야만 권한을 부여해.
④ 웹훅 시크릿과 API 키는 .env 로만 관리하고, NEXT_PUBLIC_ 에 절대 넣지 마.

결제사 [택1] 공식 문서의 웹훅 서명 검증 방식을 정확히 따라줘.
다 되면, 금액을 조작한 가짜 요청이 어떻게 거부되는지도 같이 보여줘.
```

## ✅ 여기까지 하면 이렇게 보여요

- **테스트 결제**가 서버 검증(서명·금액·중복)을 거쳐 **유료 권한이 부여**돼요.
- **금액을 조작한 요청은 거부**돼요. (이게 확인돼야 진짜 안전한 거예요.)
- 웹훅 시크릿·API 키가 `.env`에만 있고 **브라우저에 안 보여요.**
- **안 되면:** 에러 전문을 그대로 코치에게 붙이세요. 특히 "웹훅이 안 온다 / 서명 검증 실패"는 흔해요 — raw body가 아니라 가공된 데이터로 검사했을 확률이 높아요. → [[스텝08-막혔을때-에러-읽고-디버깅]]

> 코치는 "테스트 결제가 서버 검증을 거쳐 권한 부여 + 조작 금액은 거부"를 눈으로 확인한 뒤에만 `진행상태.md`의 이 줄을 `- [x]`로 바꾸고 `상태.json`을 갱신합니다.

## ⚠️ 자주 하는 실수

- **클라이언트 상태(`paid=true`)를 신뢰.** F12로 위조돼요. 결제 성공 여부는 **웹훅으로만** 확인.
- **웹훅 서명 검증 누락.** 가짜 웹훅으로 공짜 권한을 받거나, 중복 처리로 **중복 청구·"돈 냈는데 DB엔 없다"** 사고가 나요. 서명 검증 + `event.id` 중복 방지는 필수.
- **사업자등록 없이 국내 PG 시도.** 토스/포트원은 법적 판매자가 나예요. 사업자등록 없이 쓰려다 막혀요. 그 경우엔 **MoR(Lemon/Paddle)**.
- **결제 시크릿을 `NEXT_PUBLIC_`으로 노출.** AI03과 같은 대참사. 결제 키·웹훅 시크릿은 **`.env`에만**.
- **"MoR 쓰면 소득신고도 끝"이라고 착각.** MoR는 판매·각국 세금 등록을 대신할 뿐, **내 소득신고는 여전히 내 몫**이에요.
- **요금·정책을 옛 정보로 판단.** Lemon Squeezy는 Stripe 인수 후 개편 중이에요. **요율·정책은 가입 시점 공식 페이지를 꼭 확인**하세요.
