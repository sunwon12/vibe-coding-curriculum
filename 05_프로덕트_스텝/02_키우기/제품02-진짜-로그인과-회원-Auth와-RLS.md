# 제품02 — 진짜 로그인과 회원 (Auth와 RLS)

## 🎯 이 스텝에서 하는 일 (한 줄)
로그인/회원가입을 붙이고, **각 사용자가 오직 자기 데이터만 보도록** DB에 잠금장치(RLS)를 겁니다.

`⭐⭐⭐ 어려움 · 🕐 약 50분`

## 🔔 이 모듈이 필요한 신호
- 사용자마다 **자기만의 데이터**가 필요하다 (내 할 일, 내 가계부, 내 글).
- **로그인/회원가입**을 붙이고 싶다.
- "혹시 **남이 내 사용자들의 데이터를 통째로 볼 수 있는 거 아냐?**"가 걱정된다.

## 왜 이렇게 하나

지금 앱은 Supabase(수파베이스, 우리가 쓰는 무료 DB+로그인 서비스)에 연결돼 있어요. 그런데 여기 **비개발자가 거의 다 모르는 무서운 사실**이 하나 있어요.

**당신의 앱은 브라우저에서 "공개 열쇠(anon 키)"로 DB에 직접 접근해요.** 이 열쇠는 앱을 쓰는 누구나 개발자도구로 볼 수 있어요 — 원래 **공개해도 되는 것으로 설계**됐거든요. 그럼 낯선 사람이 그 공개 열쇠로 당신 DB 테이블을 **통째로 긁어가지 못하게 막는 건 뭘까요?**

딱 하나예요. **RLS(Row Level Security, 행 단위 접근 통제)**.

RLS는 DB 테이블에 거는 잠금장치예요. "이 줄(행)은 **주인만** 볼 수 있어"라는 규칙을 DB 자체에 새겨넣는 거죠. 비유하면 이래요.

| | RLS 켜짐 | RLS 꺼짐 |
|---|---|---|
| 비유 | 개인 사물함 (각자 자기 것만 열림) | **자물쇠 없는 공용 서랍** (아무나 다 열어봄) |
| 실제 | 남의 데이터 접근 시 DB가 거부 | 공개 열쇠 하나로 **전체 테이블 다운로드 가능** |

**RLS를 안 켜면 = 당신 사용자 전원의 데이터가 인터넷에 공개된 것**과 같아요. 이건 과장이 아니라, 실제로 수많은 바이브 코딩 앱이 이걸 안 켜서 데이터가 털렸어요(아래 "자주 하는 실수"에 실제 사고 정리).

### 열쇠는 두 종류 — 절대 헷갈리면 안 돼요

Supabase는 열쇠를 두 개 줘요. 이 둘의 차이가 이 스텝에서 **가장 중요**해요.

| 열쇠 | 정체 | RLS와의 관계 | 어디에 두나 |
|---|---|---|---|
| **anon / publishable** (공개 열쇠) | 공개 전제로 설계됨. 브라우저에 노출돼도 OK | **RLS가 앞을 막아줘야만 안전** | 브라우저 가능, `NEXT_PUBLIC_` 붙여도 됨 |
| **service_role** (마스터 열쇠) | **RLS를 전부 우회**하는 관리자 열쇠 | RLS 무시하고 다 뚫음 | **서버 전용. 브라우저·프론트·`NEXT_PUBLIC_` 절대 금지** |

**`service_role` 키가 브라우저에 새면 RLS를 아무리 잘 걸어도 소용없어요.** 마스터 열쇠라 잠금을 다 무시하거든요. 이건 코치에게 "이 키는 절대 프론트에 두지 마"라고 못 박아야 해요(아래 프롬프트에 넣어뒀어요).

## 이렇게 하세요

1. **코치에게 Supabase Auth(로그인) 라이브러리 설치를 맡기세요.**
   - 코치가 `@supabase/supabase-js`와 `@supabase/ssr`(서버에서 로그인 상태를 다루는 도구)을 설치해줘요.
   - 코치가 **브라우저용 클라이언트 · 서버용 클라이언트 · `middleware.ts`**(매 요청마다 로그인 토큰을 갱신해 로그인이 안 풀리게 하는 파일)를 만들어줘요. 이건 전부 코치 대행 영역이에요.

2. **이메일+비밀번호 로그인부터 켜세요.**
   - Supabase는 기본으로 이메일 로그인이 켜져 있어요. 코치가 회원가입(`signUp`)·로그인(`signInWithPassword`) 화면을 붙여줘요.
   - 먼저 이걸로 **가입 → 로그인 → 로그아웃**이 되는지 확인하고 넘어가세요. 한 번에 다 하지 말고요.

3. **(원하면) 구글 로그인을 추가하세요.**
   - 구글 클라우드에서 "OAuth 클라이언트"를 만들고, **리디렉션 주소**에 `https://<프로젝트>.supabase.co/auth/v1/callback`을 넣어야 해요(`<프로젝트>`는 코치가 알려줘요). 이 버튼 누르는 부분은 당신이, 짚어주는 건 코치가.
   - 코치가 `signInWithOAuth({ provider: 'google' })` 버튼과, 구글이 돌려보낸 사람을 로그인 상태로 바꾸는 **콜백 처리**(`exchangeCodeForSession`)를 붙여줘요.

4. **"이 사람이 로그인했나"는 반드시 `getUser()`로 확인하도록 코치에게 시키세요.**
   - 서버에서 권한을 판단할 땐 `getUser()`(또는 `getClaims()`)를 써야 해요. **`getSession()` 하나만으로 판단하면 안 돼요** — 세션 값은 위조될 수 있어서, 서버가 "진짜 이 사람 맞아?"를 Supabase에 다시 물어야 안전하거든요. 코치가 이 규칙을 지키는지 확인하세요.

5. **모든 테이블에 `user_id`를 넣고 RLS를 켜세요. (이 스텝의 핵심)**
   - 사용자 데이터가 들어가는 **모든 테이블**에 "이 줄의 주인이 누구인지" 적는 `user_id` 칸을 두고, 그 테이블의 RLS를 켠 뒤 정책을 겁니다. 복붙 SQL은 아래에 있어요.

6. **유저 두 명(A·B)으로 직접 테스트하세요.**
   - A로 가입해 데이터를 넣고, **B로 로그인해서 A의 데이터가 안 보이는지** 눈으로 확인해야 진짜예요. "잘 된 것 같아요"는 확인이 아니에요.

### RLS 핵심 규칙 (이걸 어기면 보안이 무너져요)

RLS를 "켜기만" 하면 되는 게 아니라, **정책을 제대로** 써야 해요. 초보(그리고 AI)가 가장 많이 틀리는 부분이라 규칙으로 못 박습니다.

- **테이블마다 정책 4개를 분리하세요: SELECT / INSERT / UPDATE / DELETE. `FOR ALL` 금지.** 하나로 뭉뚱그리면(`FOR ALL`) 어디가 뚫렸는지 안 보여요. 조회·생성·수정·삭제를 각각 따로 잠급니다.
- **전부 `auth.uid() = user_id`로 "본인 것만"으로 좁히세요.** 여기서 `auth.uid()`는 "지금 로그인한 사람의 ID"예요.
- **⚠️ `auth.role() = 'authenticated'`만 쓰면 그건 보안이 아니에요.** 이건 "로그인한 사람이면 통과"라는 뜻이라, **로그인한 모든 사람이 서로의 데이터를 다 봅니다.** 이게 바이브 코딩 앱 보안 사고 **1위**예요 — 조사에 따르면 RLS를 건 앱의 **약 80%**가 이 실수를 해요. 반드시 `= user_id`로 "본인"까지 좁혀야 해요.
- **성능을 위해 `(select auth.uid())`처럼 괄호로 감싸세요.** 이러면 DB가 한 번만 계산해서 훨씬 빨라요.
- **어느 정책에 무엇을 쓰는지:**

  | 정책 | `USING`(읽을/지울 자격) | `WITH CHECK`(넣을/바꿀 자격) |
  |---|---|---|
  | SELECT (조회) | ✅ | — |
  | INSERT (생성) | — | ✅ |
  | UPDATE (수정) | ✅ | ✅ (둘 다) |
  | DELETE (삭제) | ✅ | — |

- **항상 `to authenticated`를 붙이세요** (로그인 안 한 익명 사용자는 아예 대상에서 제외).

### 복붙 RLS SQL (그대로 넣으세요)

`profiles`라는 테이블 예시예요. **당신 테이블 이름으로만 바꿔서** Supabase 대시보드의 SQL Editor에 붙여넣으면 돼요(코치에게 "이걸 내 테이블에 맞게 적용해줘"라고 시켜도 됩니다).

```sql
alter table profiles enable row level security;
create policy "본인 것만 조회" on profiles for select using ( (select auth.uid()) = user_id );
create policy "본인 것만 생성" on profiles for insert to authenticated with check ( (select auth.uid()) = user_id );
create policy "본인 것만 수정" on profiles for update to authenticated using ( (select auth.uid()) = user_id ) with check ( (select auth.uid()) = user_id );
create policy "본인 것만 삭제" on profiles for delete to authenticated using ( (select auth.uid()) = user_id );
```

사용자 데이터가 들어가는 **테이블마다** 이 4줄 세트를 반복하면 돼요.

## 🤖 AI(코치)에게 줄 프롬프트

먼저 이걸로 붙이게 하세요. 안전 규칙을 프롬프트에 **박아 넣는 게 핵심**이에요.

```
계획 먼저 말해줘. 어떻게 붙일 건지 설명하고, 그다음에 하자.

You are a Supabase Postgres security expert.
내 Next.js + Supabase 앱에 인증(로그인)과 RLS를 설정해서,
각 사용자가 [예: 자기 할 일]만 접근하게 해줘. 나는 완전 초보야, 쉬운 말로 설명해줘.

반드시 지킬 규칙:
- 사용자 데이터가 있는 모든 테이블에 auth.users(id)를 참조하는 user_id 컬럼을 추가하고,
  insert 시 기본값을 (select auth.uid())로 넣어줘.
- 모든 테이블의 RLS를 켜.
- 테이블마다 SELECT·INSERT·UPDATE·DELETE 정책 4개를 분리해서 만들어(FOR ALL 금지).
- 모든 정책은 (select auth.uid()) = user_id 로 비교해. auth.role()='authenticated' 만 쓰는 건 절대 금지.
- SELECT=USING만, INSERT=WITH CHECK만, UPDATE=USING과 WITH CHECK 둘 다, DELETE=USING만, 그리고 항상 to authenticated.
- service_role 키는 프론트엔드나 NEXT_PUBLIC_ 에 절대 넣지 마. 서버 전용으로만 써.
- 서버에서 로그인 검사는 getSession()이 아니라 getUser() 또는 getClaims()로 해.

다 끝나면:
1) 모든 테이블에 RLS가 켜졌는지 확인하는 체크리스트를 줘.
2) 서로 다른 두 유저로 "A의 데이터가 B에게 안 보이는지" 테스트하는 SQL도 줘.
```

구글 로그인을 추가할 때:

```
구글 로그인을 추가하고 싶어. 구글 클라우드에서 OAuth 클라이언트를 만드는 걸
한 단계씩 손잡고 안내해줘. 리디렉션 주소로 뭘 넣어야 하는지 정확히 알려줘.
signInWithOAuth로 버튼을 붙이고, 구글이 돌려보낸 사람을 로그인시키는
콜백 처리(exchangeCodeForSession)까지 해줘. 다 되면 커밋 찍어줘.
```

## ✅ 여기까지 하면 이렇게 보여요

- **가입 → 로그인 → 로그아웃**이 됩니다.
- Supabase 대시보드의 Table Editor(또는 Authentication → Policies)에서 **모든 테이블이 RLS 초록불**(켜짐)이에요. 하나라도 회색/빨강이면 아직 안 된 거예요.
- **유저 A로 넣은 데이터가 유저 B로 로그인하면 안 보여요.** 이게 확인되면 진짜 성공이에요.
- **안 되면:** 에러 전문을 그대로 코치에게 붙이세요. 특히 "정책은 걸었는데 B한테 A 데이터가 보인다" 하면, `= user_id`가 빠지고 `auth.role()`만 걸렸을 확률이 높아요. → [[스텝09-막혔을때-에러-읽고-디버깅]]

> 코치는 "모든 테이블 RLS 초록불 + A/B 테스트 통과"를 눈으로 확인한 뒤에만 `진행상태.md`의 이 줄을 `- [x]`로 바꾸고 `상태.json`을 갱신합니다.

## ⚠️ 자주 하는 실수

- **RLS를 안 켠 채 출시.** RLS는 기본이 **꺼짐**이에요. 그냥 두면 공개예요. 실제 사고: **CVE-2025-48757** — Lovable로 만든 앱 **약 170개**에서 데이터가 유출됐고, 남의 빚 잔액·집 주소·API 키를 **15줄짜리 파이썬 스크립트**로 긁어갈 수 있었어요. Moltbook 앱은 이 문제로 **약 150만 개 토큰·이메일 3만 건**이 샜고요.
- **`auth.role()='authenticated'`만 걸기.** "로그인하면 다 봄" = 남의 데이터 다 보임. 바이브 앱 보안 사고 1위. 반드시 `= user_id`.
- **"보안 스캔 배지"만 믿기.** 스캔 도구가 "RLS 켜짐"이라고 초록불을 줘도, **정책이 실제로 본인만 막는지는 확인 안 해줘요.** 반드시 A/B 두 명으로 직접 테스트하세요.
- **`service_role` 키를 프론트에 노출.** 마스터 열쇠라 RLS를 다 우회해요. 조사에서 스캔된 앱 **약 11%**가 이 키를 유출하고 있었어요. 절대 `NEXT_PUBLIC_`에 넣지 마세요.
- **클라이언트(React)에서 버튼만 숨기고 끝내기.** 화면에서 버튼 숨기는 건 **UX(보기 편함)지 보안이 아니에요.** 공격자는 화면을 안 거치고 공개 열쇠로 DB에 직접 물어봐요. 잠금은 반드시 **DB(RLS)와 서버**에 있어야 해요.
